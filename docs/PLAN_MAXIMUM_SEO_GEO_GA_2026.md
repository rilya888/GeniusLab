# План доведения проекта до максимума (SEO + GEO + GA) — 2026

## Контекст и зафиксированные условия

1. Канонический домен проекта: `geniuslab.info` (уже подключен и работает).
2. Google tags установлены, данные уже видны в Google Analytics.
3. Старые сайты остаются отдельными проектами, 301-редиректы со старых доменов не требуются.
4. Ключевой принцип: не ломать текущую работу сайта и существующую аналитику.
5. Комментарии в коде приложения — только на английском. Русский язык — только в планах и описаниях.

---

## Цели

1. Довести тех-SEO и GEO до production-max уровня без регрессий.
2. Укрепить видимость в классическом поиске и AI-выдаче.
3. Стабилизировать операционный процесс: изменения SEO/GEO/GA предсказуемы и контролируемы.

---

## Архитектурные принципы

1. `Single source of truth` для домена, URL-политик и SEO-конфигурации.
2. Малые инкременты: каждое изменение изолировано, обратимо и проверяемо.
3. Analytics contract first: новые события не ломают текущую схему GA4.
4. Контент и schema проектируются с учетом масштабирования (новые сервисы, новые локации, новые языки).
5. Любое SEO-критичное изменение проходит release-gate и postdeploy smoke.

---

## Этап 0: Freeze baseline и контроль регрессий

1. Зафиксировать baseline:
   - текущие индексируемые URL,
   - title/description/canonical/hreflang,
   - текущие JSON-LD,
   - текущий набор GA4 событий.
2. Ввести единый release-gate:
   - `check:seo`,
   - `check:headers`,
   - smoke ключевых маршрутов.
3. Утвердить правило: SEO-критичные изменения публикуются пакетно (weekly release), hotfix — отдельно.

**DoD этапа 0**
1. Baseline документирован.
2. Проверки запускаются стабильно локально и в CI.

---

## Этап 1: Canonical и техническое SEO

1. Полная консистентность `geniuslab.info` в env/документации/фолбэках.
2. Серверная каноникализация:
   - `http -> https`,
   - `www -> non-www`,
   - единая trailing-slash policy.
3. Верификация canonical/hreflang на всех индексируемых страницах.
4. Усиление sitemap/robots контроля:
   - только публичные indexable страницы,
   - noindex-секции исключены.

**DoD этапа 1**
1. Каноникал и доменная политика полностью едины.
2. Нет конфликтов canonical/hreflang/sitemap.

---

## Этап 2: GEO и Local SEO max

1. NAP-консистентность (UI + schema + Google Business Profile).
2. Расширение LocalBusiness schema с учетом 2 точек (Lab/Store) без логических конфликтов.
3. Нормализация Service schema (`areaServed`, `inLanguage`, стабильные URL).
4. Валидировать ключевые страницы в Rich Results Test.

**DoD этапа 2**
1. Schema валидна и консистентна по всем ключевым страницам.
2. NAP не расходится между источниками.

---

## Этап 3: Контент и антиканнибализация

1. Контент-матрица:
   - страница -> целевой интент -> primary/secondary keywords -> FAQ -> CTA.
2. Антиканнибализация:
   - правила для новых сервисных страниц,
   - запрет дублирования ключевых intent-кластеров.
3. Уникализация относительно старых сайтов (без копирования крупных блоков).
4. Усиление answer-first и FAQ-блоков под AI/voice-intent.

**DoD этапа 3**
1. Для каждой целевой страницы закреплен уникальный intent.
2. Нет внутренних конкурирующих URL по одному запросному кластеру.

---

## Этап 4: Analytics quality без поломок

1. Зафиксировать event dictionary:
   - event name,
   - trigger point,
   - required params,
   - expected GA4 report usage.
2. Версионирование analytics schema (например, `analytics_schema_version`).
3. Non-breaking policy:
   - старые события не удаляются без migration window,
   - новые параметры добавляются backward-compatible.
4. Регулярная QA-проверка consent сценариев:
   - accept/reject/returning user.

**DoD этапа 4**
1. События CTA/forms/page_view приходят стабильно.
2. Consent-mode корректен, без утечки событий до согласия.

---

## Этап 5: Performance и индексируемость SPA

1. Зафиксировать performance budget (LCP/INP/CLS).
2. Контроль внешних скриптов (приоритет — не ухудшать CWV).
3. Проверка head-актуальности после SPA-навигации.
4. Приоритетная оптимизация ключевых коммерческих страниц.

**DoD этапа 5**
1. Пороговые CWV выдерживаются на целевых страницах.
2. Head-данные после клиентских переходов корректны.

---

## Этап 6: OPS, ownership, SLA, release governance

1. Назначить владельцев направлений:
   - SEO owner,
   - GEO/GBP owner,
   - Analytics owner,
   - Release owner.
2. Ввести SLA:
   - критичный инцидент (analytics drop/массовые 404) — реакция до 30 минут.
3. Change management:
   - weekly SEO release train,
   - запрет смешивать в одном релизе крупный роутинг + schema + analytics refactor без расширенного QA.
4. Ввести weekly ritual (30-45 минут):
   - SEO + GA + GEO checklist,
   - фиксация action items.

**DoD этапа 6**
1. Регламенты задокументированы и реально используются.
2. Есть журнал weekly проверок и инцидентов.

---

## Этап 7: AI-visibility roadmap (Phase 2)

1. Добавить KPI AI-видимости после стабилизации базового SEO/GEO:
   - AI referral traffic,
   - coverage answer-first контента,
   - рост branded/non-branded видимости.
2. Расширять контентные сущности и FAQ-покрытие без переспама.
3. Отдельно контролировать качество фактов и консистентность NAP/услуг в AI-friendly блоках.

**DoD этапа 7**
1. AI-KPI встроены в регулярный отчетный цикл.
2. Рост AI-видимости измеряется, а не оценивается субъективно.

---

## Операционный ритм (обязательный)

1. Weekly SEO/GA/GEO review — 30-45 минут.
2. Еженедельный релиз SEO-критичных изменений (кроме hotfix).
3. Каждый релиз:
   - pre-release gate,
   - postdeploy smoke,
   - короткий verification report.

---

## Definition of Done (максимум)

1. Единая каноничность `geniuslab.info` реализована на 100%.
2. SEO/GEO структура покрывает все ключевые страницы и интенты.
3. GA4 работает без регрессий при любом штатном релизе.
4. Есть рабочий OPS-процесс: ownership, SLA, weekly ritual, release policy.
5. Проект готов к масштабированию (новые сервисы/локации/локали) без архитектурной миграции.
